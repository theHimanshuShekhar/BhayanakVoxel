# Custom engine in Rust + wgpu, Vulkan only

BhayanakVoxel is built as a custom engine in Rust on wgpu, with a pinned wgpu version, WGSL shaders and Vulkan as the only supported backend. We chose it over Bevy, Godot, Unreal, raw Vulkan and C++. No engine provides the hard parts (micro-Voxel storage, the voxel path tracer, Zoom-to-orbit LOD), so an engine would mostly have saved glue code that agents write easily anyway. Rust also gives bit-identical Planet generation on every machine by default, while C++ needs strict float flags on each compiler. The dedicated server is a separate binary that never links wgpu.

## Considered Options

- **Bevy:** the closest runner-up. Rejected because it ships breaking API changes about every quarter, agents' knowledge of it tends to be stale, and its render graph would sit between us and the voxel tracer.
- **C++ + Vulkan:** the most RT material and prior art (gvox_engine). Rejected for determinism fragility and memory and synchronization bugs a beginner can't easily supervise.
- **Raw Vulkan from Rust (ash):** mostly `unsafe`, with a stale crates.io release. Kept only as an escape hatch through wgpu's `as_hal` if hardware ray tracing or NRD/DLSS ever require it.
- **Godot, Unreal:** mesh-centric renderers we would mostly bypass.

## Consequences

- Hardware ray queries in wgpu are experimental, so M1 lighting is built on compute-shader ray marching: every pass goes through one `trace()` and is tuned on the compute path. Hardware ray queries were a time-boxed spike after GI (#50, re-ordered 2026-11-10), adopted only if they were faster on real secondary rays; no lighting ticket waited for them.
- **Amended 2026-11-27 (#50 Part 2): hardware ray queries are the default.** They were faster on every ray pass on the 4090 (PR #233) and the owner adopted them on 2026-11-21: they run wherever the adapter has `EXPERIMENTAL_RAY_QUERY`, the player's setting switches to the compute walk (for a GPU that they do not suit), and an adapter without them runs compute with no error. The compute `trace()` stays: it is the fallback, the setting, and the CPU-checkable reference (`reference.rs`), and both backends enter a brick through the same tight box. The cost of the default is the opt-in to wgpu's experimental ray queries (their `unsafe` opt-in is made whenever the adapter has them), which a wgpu upgrade re-checks.
- **Amended 2026-11-28 (#260): the opt-in follows the setting.** This supersedes the 2026-11-27 amendment's "whenever the adapter has them". The window's device asks for `EXPERIMENTAL_RAY_QUERY` and makes wgpu's `unsafe` experimental opt-in only if the setting is hardware, the adapter has ray queries and the run is not held to none (`--profile low-end`, `--no-ray-queries`, `BHAYANAK_RAY_QUERIES=0`, #264). The compute setting, and the low-end profile, make a device with none of it, so a driver or a wgpu path that chokes on the experimental features cannot stop the game from starting. The features of a device are fixed when it is made, so a switch of the setting at run time works at once in what runs (compute, or hardware where the device has them) but changes the device only at the next launch, and the overlay says so: a switch to hardware on a device made without them runs compute until a restart. If the request for a device with them fails, the client asks once more without them, runs compute, and says so in the log and the overlay; it does not exit, and the next launch tries again (the compute setting skips it).
- NVIDIA-only denoisers and upscalers (NRD, DLSS) need native interop.
- Each wgpu upgrade is a deliberate task that comes with its migration guide.
- One dependency under wgpu is patched: `third_party/gpu-allocator` (0.28.0) keeps up to two empty memory blocks instead of destroying them and making one again on the frame that needs it, which stalled the GPU for about 6.5 ms (#236, `third_party/gpu-allocator/PATCH.md`). A wgpu upgrade checks that wgpu-hal still takes that version, and whether the patch is still needed.
